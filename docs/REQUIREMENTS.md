# 产品与系统需求

> 状态：D-025/D-026 已冻结协议 v2 与三端当前目标，D-027 手机首次寻星约 2.8 秒、可见性门及 normal-motion 自动浏览器断言已落地并通过；V2-00～V2-09 已实现协议、服务端、三端页面、三浏览器自动回归与 300 人协议负载，V2-10 的 30 分钟自动渲染 soak 已通过，仓库实际 `.data` 仍未切换。D-027 自动子门为 `PASS`；vivo X300 复验、三端局域网与 OBS 实际合成人工验收仍为 `PENDING`。D-022 冻结的 G0～G4 与 D-023/D-024 对应条款、实现和证据均归入 v1 历史基线。
> 说明：`V2-MUST` 才表示当前实现目标；`G3-EXIT`、`G4-EXIT`、`G5-EXIT` 与下方标明 v1 的 `MUST` 只保留历史取证，不能证明 v2 已实现。若旧条款与本文件第 3 节或 [`PROTOCOL_V2.md`](./PROTOCOL_V2.md) 冲突，以 D-025/D-027 v2 为准。`FORMAL-PENDING` 仍表示正式上线前确认。

## 1. 角色

- **Demo 参与者**：优先通过固定合成邀请令牌进入 H5；二维码/短链接携带同一令牌，人工协助可使用虚构姓名和合成学号定位同一身份与状态，不得建立第二账号。
- **共用后台操作会话**：登录后可自行取得 `REVIEWER`、`STAGE_CONTROLLER`、`DEMO_ADMIN` 或 `ALL`；不同角色只是能力分组。
- **大屏会话**：读取聚合数据、公开星号/星色、仍处于公开状态的弹幕，以及后台人工选中的时光胶囊。
- **项目负责人**：当前长期单人维护，并负责产品取舍、运行和最终验收。

## 2. 入口与身份

- **REQ-ENTRY-001 MUST**：Demo v0 使用同一随机令牌验证 NFC 与二维码的入口概念；NFC 作为正式产品主入口、二维码作为设备兼容备用的方向保持不变，但实体写卡和印刷为 `FORMAL-PENDING`。
- **REQ-ENTRY-002 MUST**：NFC、携带同令牌的二维码/短链接及 Demo 人工协助核验进入同一 H5，并恢复同一个参与者状态；不得重复发放动力值或生成两个档案。
- **REQ-ENTRY-003 MUST**：NFC、二维码和可见链接不得直接包含姓名、学号、班级等个人信息。
- **REQ-ENTRY-004 MUST**：页面应提供清晰的轻触、扫码和人工协助说明。
- **REQ-ENTRY-005 MUST**：后台应能识别有效、无效或已作废的合成入口；令牌操作需要 `DEMO_ADMIN` 或 `ALL` 当前角色和确认对话框。
- **REQ-ENTRY-006 MUST**：采用个性化“一人一卡一码”；同卡 NFC 与二维码编码同一不可猜测随机令牌，确定性重置后保持有效。
- **REQ-ENTRY-007 MUST**：入口 URL 可承载随机令牌；前端读取并发起激活后应立即将地址栏和当前历史项替换为不含令牌的 `/welcome`，且不得将令牌发送给第三方资源或写入日志。
- **REQ-ID-001 MUST / G5-EXIT**：个性 NFC 令牌是主要核验方式；二维码/短链接携带同一随机令牌。Demo 人工协助可使用虚构姓名和合成学号定位同一合成身份，但必须恢复该身份既有状态，不得生成第二账号；失败信息不得分别泄露姓名或学号是否存在。
- **REQ-ID-002 MUST / G5-EXIT**：公开星号由合成姓氏拼音首字母和合成学号后四位组成，例如 `L-4821`；系统必须在身份目录导入和数据库层校验唯一性，碰撞时拒绝该目录/身份启用。该编号可能被熟人关联到本人，不得称为不可关联匿名 ID。
- **REQ-ID-003 MUST**：同一参与者可在多个设备或浏览器同时保持会话；各端恢复同一服务端状态。
- **REQ-ID-004 FORMAL-PENDING**：正式真实名单来源、学号核验授权、人工核验、访客权限和碰撞应急规则后续确认。

## 3. 协议 v2 当前要求

### 3.1 版本与权威状态

- **REQ-V2-PROTOCOL-001 V2-MUST**：命令请求、快照、响应、持久化和实时事件必须明确携带 `protocolVersion=2` 与当前 `resetEpoch`；v1 与 v2 不得在同一运行实例中混用。共享契约统一使用 `runRevision`、`presentationRevision`、`participantRevision`、`aggregateRevision`、`starRevision`、`interactionRevision`，以及 `public|admin|participant:<id>` 各流独立连续的 `streamSeq`。稳定事件名以 [`PROTOCOL_V2.md`](./PROTOCOL_V2.md) 第 4.3 节的闭合集合为准；任一受限流事件不能推进其他流或制造伪缺口。
- **REQ-V2-PROTOCOL-002 V2-MUST**：合法运行 tuple 只有：任一 mode 的 `READY+null`、任一 mode 的 `RUNNING/PAUSED+三个场景之一`，以及唯一 `LIVE+COMPLETED+COOPERATIVE_LIGHT`。不存在 `REHEARSAL+COMPLETED`、第六阶段或 `ARCHIVE` 场景。
- **REQ-V2-PROTOCOL-003 V2-MUST**：LIVE 的最终操作由最后场景发起一次确认，服务端原子写入 `COMPLETED`；不得依赖动画回调，也不得再要求第二次“进入第六阶段/完成”。REHEARSAL 只能显式预演结尾画面，不得修改 LIVE 的 `COMPLETED` 事实。
- **REQ-V2-PROTOCOL-004 V2-MUST**：`PAUSED` 拒绝参与者业务写入，但允许已激活身份只读重认证、权威恢复和公开内容处置；`COMPLETED` 硬性关闭参与者写入，任何本 epoch 已激活身份可只读重认证，后台仍可删除、屏蔽、清屏或撤下公开内容。“安全处置”不包含扣减/补发动力值或星光。
- **REQ-V2-PROTOCOL-005 V2-MUST**：`SET_MODE` 仅 READY；`START` 从 READY 进入 ASSEMBLY；REHEARSAL 的 `SET_SCENE` 仅 RUNNING 且可跳三场景；LIVE 的 `ADVANCE` 仅按三场景向前；`PAUSE` 仅 RUNNING，`RESUME` 仅 PAUSED；LIVE 的 `COMPLETE` 仅 `RUNNING+COOPERATIVE_LIGHT`。非法 tuple、迁移或过期 revision 必须稳定拒绝。
- **REQ-V2-PROTOCOL-006 V2-MUST**：服务端稳定错误码是 [`PROTOCOL_V2.md`](./PROTOCOL_V2.md) 第 9 节列出的闭合集合，覆盖认证/权限/校验、版本/epoch、运行门、容量、入场、场景/revision/readiness、幂等、余额、内容/来源/限频和服务不可用；V2-01 不得暗中继承其他 v1 码。离线是客户端条件，不得冒充服务端错误。
- **REQ-V2-PROTOCOL-007 V2-MUST**：参与者快照必须携带完整个人入场/胶囊/数值/场景事实以及服务端计算的 `allowedActions`；运行或个人事实事件、epoch 变化和序列缺口后先刷新快照再启用写入。三端不得各自发明不同的动作门禁，命令事务仍必须重查最新权威状态。

### 3.2 参与者入场与晚到者

- **REQ-V2-ONBOARD-001 V2-MUST**：有效 NFC/同令牌备用入口或映射同一合成身份的人工协助核验成功时，服务端必须先原子预留一个不透明稳定 formation slot，再完成身份激活、建立唯一会话/状态并只发放一次 100 动力值和 20 星光，参与者进入 `NEEDS_COLOR`；容量满时整笔激活以 `STAR_CAPACITY_REACHED` 拒绝，不得建状态或发奖励。
- **REQ-V2-ONBOARD-002 V2-MUST**：`READY` 和 `RUNNING` 均允许新参与者或晚到者完成入场。晚到者完成信息或明确跳过后直接进入当前全场状态，不补播已错过场景。
- **REQ-V2-ONBOARD-003 V2-MUST**：参与者锁定星色后进入 `NEEDS_CAPSULE_DECISION`，并把预留恒星以唯一 `publicStarId`、稳定槽位和 `starRevision` 原子加入公开星系，发布 `star.node.upserted`；本人端突出显示并标注本人星号，其他恒星在普通参与者界面不显示标签。
- **REQ-V2-ONBOARD-004 V2-MUST**：时光胶囊决定必须持久化为 `SUBMITTED` 或 `SKIPPED`。`SUBMITTED` 最多 80 个可见字符且必须明确确认进入人工公开候选池，不允许“提交但不入池”；首次实际提交奖励 20 星光。跳过当时奖励 0，但可在 `READY` 或 `RUNNING` 后补填，首次成功补填仍只奖励一次，且不得改变原 `admittedAt`。
- **REQ-V2-ONBOARD-005 V2-MUST**：完成胶囊提交或跳过后进入 `ADMITTED`。重复请求、刷新、多设备、断线恢复和并发不得重复激活、重复锁色、重复加入星系或重复奖励。
- **REQ-V2-ONBOARD-006 V2-MUST**：`PAUSED` 期间不接受首次激活、锁色、胶囊提交/跳过/补填等参与者写入；已激活身份可建立只读会话。`COMPLETED` 后任何本 epoch 已激活身份（包括未完成入场者）可重新核验并只读查看现有事实，但不得继续入场、创建新参与者或修改资料。

### 3.3 星系与全场场景

- **REQ-V2-GALAXY-001 V2-MUST**：公开星系最多承载 300 颗真实参与者恒星，不用虚构参与者补位，也不得静默截断。formation slot 从固定、不透明的确定性目录在首次激活事务中预留；容量满时拒绝首次激活，不得先发奖励再让参与者卡在锁色。
- **REQ-V2-GALAXY-002 V2-MUST**：客户端先获取带 `resetEpoch`、各类 revision 与获授权 `streamSeq` 游标的权威快照，再按逻辑流消费幂等事件；刷新、重连、跨流交错、乱序、缺口和事件重放不得制造重复恒星、伪缺口或改变既有槽位。
- **REQ-V2-SCENE-001 V2-MUST**：`ASSEMBLY` 只允许 `ADMITTED` 参与者执行一次 `START_STAR`，写私有 `started/startedAt`，原位更新公共恒星 `started=true`、递增 `starRevision`、发布完整 `star.node.upserted` 并发 20 星光，但不创建或移动恒星；`PROGRAM_SUPPORT` 才允许礼物与弹幕；`COOPERATIVE_LIGHT` 才允许一次性协同点亮。晚到者不得补做已离开场景的操作或补领旧场景奖励。
- **REQ-V2-SCENE-002 V2-MUST**：presentation 为服务端权威互斥状态 `NONE|CAPSULE_INSERT|FINALE_PREVIEW`，使用独立 `presentationRevision`，不改变 `runRevision`。胶囊插入由 REVIEWER/ALL 人工触发且每次最多 6 条，不自动轮播、不由规则或 AI 自动公开；REHEARSAL 结尾预览只允许 `RUNNING+COOPERATIVE_LIGHT+NONE`，必须持续标记并可手动清除。
- **REQ-V2-SCENE-003 V2-MUST**：场景变化、暂停和重置清除活动 presentation；LIVE 完成在同一事务中捕获当前插入的最多 6 条胶囊到终局 recap 后清为 `NONE`。`COMPLETED` 后不得新增展示，但允许经权限、确认和审计安全撤下 recap 内容。
- **REQ-V2-SCENE-004 V2-MUST**：大屏快照的每颗公共恒星必须含 `started`，安全聚合至少区分激活、公开恒星、已准入、已启动、协同点亮与星光总量。后台以匿名漏斗区分激活、锁色入星系、准入、胶囊已提交/已跳过及入场未完成，不以在线会话数作人数分母，也不暴露逐人身份。
- **REQ-V2-SCENE-005 V2-MUST**：`ADVANCE`/`COMPLETE` 将适用的匿名就绪警告合并进原有一次确认；人数/完成度警告允许有权限操作者明确 override，但权限、旧 revision/epoch、非法 tuple、离线或未知结果不可 override。服务端在事务中重算并审计确认时的匿名摘要。
- **REQ-V2-SCENE-006 V2-MUST**：胶囊审核状态按 `SUBMITTED→SELECTED→DISPLAYED` 管理，撤下为 `REMOVED`；选择、展示、清除、修改、撤下和终局捕获的唯一迁移、participant/presentation revision 与事件必须遵守协议第 5.1 节，不得让空插入投影、旧正文或隐式选择继续公开。

### 3.4 大屏、OBS 与公共互动

- **REQ-V2-SCREEN-001 V2-MUST**：大屏最多显示 300 颗真实公共恒星，使用单 Canvas 与稳定 `formationSlot`；不得补装饰恒星冒充参与者，不得显示任何参与者编号/公开星号、排行、头像或可点击个人节点。
- **REQ-V2-SCREEN-002 V2-MUST**：`ASSEMBLY` 使用完整星系，`PROGRAM_SUPPORT` 作为 OBS 透明浏览器源，只在左右边缘约 15%～20% 保留弱星系并覆盖匿名弹幕/礼物，`COOPERATIVE_LIGHT` 恢复全屏协同点亮。节目视频与音频由 OBS/导播拥有，网页不得上传、播放或控制媒体。
- **REQ-V2-SCREEN-003 V2-MUST**：规则通过的弹幕以匿名公共事件上屏；正文最多 40 个用户感知字符，单参与者最多 3 条/10 秒，全场最多 12 条/秒，并拒绝敏感词、链接、联系方式、暂停状态和已屏蔽来源。Screen 快照/事件不得含来源或参与者身份；Admin 只取得不可展示、不可导出的匿名 `sourceId` 用于审核。
- **REQ-V2-SCREEN-004 V2-MUST**：后台必须能暂停新弹幕、带原因撤下单条、屏蔽匿名来源并撤下其内容、紧急清屏；命令复核角色、revision、确认与幂等，并留下审核记录。`COMPLETED` 后只允许减少公开内容，不得重新发布、补发或扣减数值。
- **REQ-V2-SCREEN-005 V2-MUST**：礼物公共事件只包含节目、礼物 ID/名称和时间，不含发送者；1.5 秒内同类事件可在视觉上合并，大屏同时最多保留一个主礼物和一个次礼物。星舰可更突出但必须限时，并服从终章、预览、胶囊和故障层。
- **REQ-V2-SCREEN-006 V2-MUST**：胶囊插入独占大屏视觉；期间弹幕/礼物仍按权威事务持久化，但不得排队补播。视觉优先级固定为 `COMPLETED > FINALE_PREVIEW > CAPSULE_INSERT > 故障提示 > 当前场景 > 实时互动`。
- **REQ-V2-SCREEN-007 V2-MUST**：LIVE 完成只在从非完成态实时观察到权威事件时播放约 5～6 秒收束；首次快照已完成、刷新、重连和 reduced-motion 直接进入相同稳定终态。排练终章持续标明“排练预览”，不得暗示活动已结束。
- **REQ-V2-SCREEN-008 V2-MUST**：V2-07 允许 `/screen` 按需加载 GSAP core，仅驱动少量覆层的 transform/opacity；300 星点必须继续由 Canvas 绘制。不得引入 GSAP 插件、逐星时间线、持续 blur/filter、动画业务回调或借此提前迁移手机端。

### 3.5 手机信息架构与动效

- **REQ-V2-MOBILE-001 V2-MUST**：手机主页面使用沉浸式流动星系和一个克制的底部液态玻璃操作坞；不得恢复六阶段直线、原始 `RUNNING` 文案、常驻“实时同步”文字或玻璃卡片墙。液态玻璃不可用时提供可读的不透明降级，且不得使用持续动画模糊/滤镜。
- **REQ-V2-MOBILE-002 V2-MUST**：任务成功提示约 3.5 秒自动收回，并由页面上的持久权威状态取代；错误、离线、暂停和完成提示保持可见直到状态改变或用户处理。
- **REQ-V2-MOTION-001 V2-MUST**：正常首次核验成功、服务端明确返回新建身份与 `NEEDS_COLOR` 后，页面必须先等待稳定 `visible`，再播放约 2.8 秒、更具穿越感的星云/寻星过场；色温选择不计时；权威锁色成功并取得星系快照后播放约 1.2 秒“点亮本人恒星并拉远进入星系”过场。
- **REQ-V2-MOTION-002 V2-MUST**：正常首次入场不提供跳过动画按钮。开始前暂不可见时等待；镜头真正开始后进入后台或被中断时立即收束到静态权威终态，返回不重播。减少动态效果、返回用户、刷新、断线恢复、失败或超时也直接显示静态可操作终态。体验中不再使用怀士堂或任何建筑轮廓。
- **REQ-V2-MOTION-003 V2-MUST**：首次叙事镜头使用 Vue 与 CSS 的低成本 `transform`/`opacity`，Canvas 只承担权威星系；D-026 的 GSAP core 例外只适用于 V2-07 `/screen`。手机不得继承该依赖，任何动效均不得承载、推进或延迟唯一业务提交事实。
- **REQ-V2-MOTION-004 V2-MUST / AUTO-PASS**：真实临时 v2 栈、生产 Vue 页面、新鲜邀请与 normal-motion 的聚焦浏览器回归已通过，证明稳定可见后进入约 2.8 秒首次镜头、无跳过、开播后后台中断静态，以及刷新/恢复/reduced-motion 不重播。既有 reduced-motion 三端 E2E 和只等待选色终态的桌面 smoke 仍不得代替该证据；vivo X300 人工复验仍为 `PENDING`。

### 3.6 数值与可变权重

- **REQ-V2-VALUE-001 V2-MUST**：当前星光规则为激活 20、首次实际胶囊提交 20、首次星星启动 20、首次送礼 10、首次规则通过弹幕 10、首次协同点亮 20；胶囊跳过奖励 0。
- **REQ-V2-VALUE-002 V2-MUST**：奖励事件权重必须服务端版本化；每个 `resetEpoch` 固定一个 `rewardRuleVersion`，每行账本保存实际增量和版本。后续调整只能从新 epoch/规则集生效，不得热切换或改写历史账本。当前上限为 100；当前不实现抽奖、中奖概率或兑奖，未来概率只能读取权威星光，不得从客户端推算。
- **REQ-V2-VALUE-003 V2-MUST**：本协议不提供后台扣减/补发动力值或星光的功能；终局前后的安全处理仅指删除、屏蔽、清屏或撤下公开内容。

### 3.7 普通重置与一次性切换

- **REQ-V2-RESET-001 V2-MUST**：`RESET_DEMO` 可从任意合法 tuple 显式发起，但必须由 `DEMO_ADMIN`/`ALL`、确认对话框和合成数据硬门共同授权；发现真实、个人、不可重建或有保留价值的数据即停止，且永不在服务启动时自动执行。
