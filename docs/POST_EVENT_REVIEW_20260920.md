# 2026 迎新晚会赛后审阅与下一届改进包

日期：2026-09-20
审阅对象：`SYSU-Welcome-Interactive` 当前工作树及 `docs/D113_FIELD_TEST_CHECKLIST_20260918.md`、`docs/D114_IMPLEMENTATION.md`、`docs/D118_IMPLEMENTATION.md`、`docs/D119_IMPLEMENTATION.md`、`docs/D121_IMPLEMENTATION.md` 记录。
目的：把本届晚会的流程、创意、代码落点、现场风险和下一届可执行的改进集中交接。

## 先给下一届的结论

这不是一个只有页面的 Demo，而是一套把手机观众、大屏叙事、后台控台、节目单、奖项、OBS 和数据库状态放在同一协议下的现场系统。它最有价值的部分是：所有关键动作有状态、有权限、有恢复路径；手机不把未确认操作偷偷排队；大屏和后台都能在实时连接恢复后重新取权威快照；现场还准备了不依赖网页和网络的手动翻页舞台包。

本届最需要正视的缺口是开场的网络依赖。昨晚网络故障时，网页舞台无法按原流程开始，说明“系统有重连”不等于“晚会能离线开场”。当前代码里的 `offline` 状态只负责停止提交、显示离线并重连；D-114 的 48 页 PPT/PDF 是人工备用物料，不是应用内自动接管。下一届应把离线开场升级为正式的双轨方案：开场与节目推进至少能在本地主控机上脱离外网运行，联网恢复后再安全回接互动数据。

## 流程审阅

### 做得好的地方

1. **先验证再推进。** `LIVE_OPERATOR_GUIDE.md`、`HOST_CUE_GUIDE.md` 和 D-113 把主控、主持、OBS、NFC、网络/设备负责人拆开，并要求在开始前核对 `/welcome`、`/screen`、`/admin`、`/api/ready`、目录和 OBS 桥接状态。
2. **现场动作被建模为状态机。** 后台不是直接改页面，而是通过协议和运行状态推进 `READY → RUNNING → PAUSED/COMPLETED`，节目切换、互动开启、奖项揭晓和收尾都有边界。未知节目或重复映射会拒绝执行，避免“猜一个场景继续播”。
3. **观众体验有明确叙事。** 每位入场者拥有个人星色和匿名星体；礼物、弹幕、节目背景、互动和片尾都围绕“星光”主线。手机端和大屏端各自取景，但共享节目和现场状态。
4. **数据和权限边界清楚。** 学生、工作人员、游客、后台管理员有不同能力；公共大屏只显示已揭晓姓名，不显示备注、学号或内部说明；正式名单、运行密钥、NFC 映射要求放在代码目录之外。
5. **恢复意识已经进入代码。** WebSocket 断开后会重新取快照再带 `resetEpoch`/`afterEventSeq` 建立连接；音频桥接有心跳、动作确认和 `mix` 输入校验；数据库启动前会检查 schema、seed 和就绪状态。
6. **有真实的人工交接材料。** D-113 把线缆、备用电脑、热点、充电、NFC 补卡、纸质口令单和 OBS 场景集合列为必备物资，这比只交源码更接近真正的晚会运行要求。

### 暴露出的缺点

1. **开场仍有单点网络依赖。** `/welcome`、`/screen`、`/admin` 和实时通道默认依赖同一后端及局域网/反向代理。客户端能显示离线并重连，但离线时不能提交互动；这无法保证主持人在网络中断时准时开始。
2. **离线物料和在线状态没有形成一个切换器。** D-114 已生成 48 页手动 PPT/PDF，但切换靠人发现故障后执行；没有一份“主控电脑一键切换到离线舞台”的可执行入口，也没有把当前节目、舞台模式、音频和回切规则记录成机器可读状态。
3. **发布与现场交接过于依赖熟悉项目的人。** D-110 至 D-121 连续累积了大量现场修正，说明系统能快速响应，但下一届若只拿到源码和零散 D 文档，仍需要原作者解释“哪份是当前规则”。应维护一个版本清单、一次彩排脚本和一页故障决策树。
4. **自动化验证和现场验证存在边界。** 当前测试覆盖构建、协议、集成、浏览器和部分 OBS 检查；真机、LED、调音台、NFC 实体写卡、真实音频播放和场馆网络仍需要人工签核。浏览器绿色不能代表现场绿色。
5. **OBS 与网页是两个动作。** 这是安全的分工，但也增加了操作负担。主持报幕、后台执行、OBS 播放/切场若没有口令复诵和回读，仍可能出现画面、音乐、倒计时不同步。
6. **工作树和历史包较重。** 当前目录含大量恢复副本、构建产物和连续阶段记录；本次已把 `.welcome-recovery/` 排除，下一届仍应以“源码 + 可复现脚本 + 脱敏示例数据 + 一份 release manifest”为主，避免把本地备份误当成发布包。

## 下一届改进顺序

### P0：把昨晚的网络问题变成可演练的双轨方案

- 在主控电脑本地提供一个静态舞台包入口，至少包含开场、19 个节目、互动标题、颁奖和结束页。
- 增加“离线舞台”状态：网页/OBS 桥接不可用时，主控可以明确切换；屏幕显示当前模式，主持单写明何时切换、何时回到在线。
- 离线模式不假装保存互动数据；把“不可用的互动”显示为人工口令或跳过，并在回线后由主控确认再恢复在线。
- 彩排时拔掉主网络、关闭服务器访问，完整跑一遍开场至结束；PASS 才能进入正式晚会。

### P1：减少人脑记忆和跨设备同步

- 生成一份 `RELEASE_MANIFEST.json`：源码 commit、前端包 hash、后端包 hash、节目目录 hash、OBS 场景集合版本、离线包 hash、数据库 schema。
- 主控页提供“当前节目 / 当前舞台模式 / OBS 回读 / 音频桥接 / 网络状态”单屏摘要，并把关键动作写入本地脱敏日志。
- 主持口令、OBS 操作单、现场测试表和离线页从同一个节目目录生成，避免文档与代码漂移。

### P2：把现场验收变成有证据的发布门槛

- 预演前：`pnpm docs:check`、`pnpm typecheck`、`pnpm test`、`pnpm build:formal`。
- 预演中：三端访问、真实手机、NFC 样卡、LED、OBS WebSocket、三组音频、断网切换、恢复回线。
- 发布后：健康检查、就绪检查、当前轮次/目录/场景回读、截图和 hash 归档；没有证据的项目标记 `PENDING`，不能写成“已完成”。

## 本次打包边界

- GitHub 包应包含源码、脱敏示例配置、迁移、测试、流程文档、主持/主控手册和可复现构建脚本。
- 不应上传正式名单、学号、密码、NFC 私密映射、OBS 密码、桥接令牌、Cookie、真实备份数据库或 `.welcome-recovery/`。
- `output/` 和本地测试账号继续保持忽略；若下一届需要离线 PPT，应通过脚本重新生成，或把不含个人信息的最终静态包作为单独 release artifact 发布。

## 验证边界

本审阅基于当前工作树、代码搜索和 D-113/D-114/D-118/D-119/D-121 的记录；没有把历史文档中的 PASS 自动当作今晚的现场 PASS。当前仍需人工确认的项目包括：真实场馆网络、手机真机、NFC 实体卡、LED 清晰度、调音台、OBS 真实播放和离线切换演练。
