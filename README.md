# SYSU Welcome Interactive

中山大学智能工程学院迎新晚会创新互动网页项目。

正式产品采用 NFC 明信片邀请函作为主要体验入口，二维码和短网址作为设备兼容备用；三种方式进入同一 H5。Demo v0 只验证同一随机令牌的网页入口，实体制作后续确认。二维码不能解决网站或现场网络故障，相关情况由备用网络、轻量页面和离线流程处理。

## 当前状态

Demo v0 的 G0～G4 源码基线已于 2026-08-10 在提交前工作树完成验收：G0 冻结产品、隐私、风险与延期边界；G1 建立可信技术底座；G2 实现六阶段三端真实闭环；G3 的桌面三浏览器自动化和 vivo X300 默认浏览器人工核心旅程均通过；G4 用 300 个固定合成参与者完成本机 HTTP/WebSocket 混合旅程、传播延迟、不变量、重启和重置验证。根级 `pnpm verify:g4` 提交前全门退出码为 0，D-021 验收未发现或复现未关闭 S0/S1。该结果由 D-021 与 [`docs/ACCEPTANCE_G0_G4.md`](./docs/ACCEPTANCE_G0_G4.md) 记录，不自动证明任何提交。G0～G4 冻结候选提交形成后，必须在该提交的干净工作树重跑适用门禁，并由 D-022 记录被验收提交的完整 SHA、命令结果与工作树状态；D-022 落地前只能称为冻结候选，不能称为可复现冻结版本。G5 Orbital Signal 视觉与动效仍是下一阶段。所有运行数据仍是固定合成数据，不包含真实名单、生产密钥、实体 NFC、公网部署或正式活动数据。

- `frontend/`：Vue 3 + Vite；含可操作的 `/welcome`、`/screen`、`/admin` 三端页面。
- `backend/`：Node.js/TypeScript + Fastify + SQLite 本地服务；运行数据库和凭据只生成在被忽略的 `.data/`。
- `packages/contracts/`：前后端共享的协议版本、错误、运行状态、健康检查、快照和实时事件契约。
- `docs/`：需求、决策、隐私、测试和现场手册。
- `tests/`：G1/G2 自动化测试、G3 浏览器端到端与恢复测试、G4 协议级负载、真实设备和最终验收说明。
- `.github/`：Issue、Pull Request 和自动构建模板。

## G0～G4 验收与复验

需要 Node.js 和 pnpm。

```bash
pnpm install --frozen-lockfile
pnpm dev
```

根命令会初始化本地合成数据，依次启动后端和前端，确认代理链路就绪后输出手机入口、后台、大屏和二维码文件位置。手机与电脑需位于同一可信网络；启动器不会修改 Windows 防火墙。首次运行生成的合成入口、六位 Demo 码、后台口令和数据库只保存在 `backend/.data/`，不得提交或截图传播。

先验证 G2 功能基线：

```bash
pnpm verify:g2
pnpm db:verify
```

G3 自动化从仓库根目录运行：

```bash
pnpm verify:g3
```

作为 D-019 的历史独立 G3 基线，2026-08-10 的 `pnpm verify:g3` 曾以退出码 0、总时长 278.9 秒收口：Vitest 16 个测试文件、102 条测试全部通过；Playwright 6 个场景在 `chromium-ci`、系统 Chrome 和系统 Edge 三个项目各执行一次，合计 18/18；共享契约、后端和前端生产构建全部通过，退出后 E2E 临时目录为 0。D-021 的提交前工作树总验收重新执行扩展全门：`pnpm verify:g4` 退出码 0、观察总时长约 463.2 秒，Vitest 20 个测试文件/119 条全部通过，共享契约、后端与前端生产构建通过；Playwright 9 个场景 × 3 个项目 = 27/27，各项目 9/9，报告状态 `passed`、失败检查点 0、浏览器报告窗口 295388 ms。新增的 `session-races.spec.ts` 覆盖参与者退出晚到快照、后台快速重登和外部重置后的私密 DOM 清理，`recovery` 与 `three-surfaces` 已记录静态失败检查点。

D-021 的运行环境为 Windows 10.0.26100、Node.js 24.16.0、pnpm 11.16.0、Playwright 1.62.1；浏览器分别为 Chromium 151.0.7922.34、Chrome 151.0.7922.76、Edge 151.0.4129.72。机器可读浏览器报告是被 Git 忽略的本地脱敏证据，不是提交产物。CI 已配置，但尚无远端执行证据，不能算作 D-021 通过依据。

启动后可用共用后台账号进入 `/admin`，先取得需要的 Demo 角色，再启动排练或现场流程；参与者从启动器生成的带合成令牌入口进入 `/welcome`，大屏使用 `/screen`。刷新、重复提交、短暂断线和服务重启均以服务端权威状态恢复；确定性重置会恢复固定合成目录并让旧会话失效。

G2 完成的是“真实可操作”的功能基线，不等于最终视觉或正式现场验收。D-021 记录 G3 的桌面浏览器自动化与 vivo X300 默认浏览器人工核心旅程均通过，且未发现或复现未关闭 S0/S1；真机浏览器版本和实际 CSS 视口未单独采集的限制已在验收记录中接受。D-021 记录 G4 的 300 人本机协议负载专项通过，但不替代 30 分钟 soak、分布式局域网、场馆或正式上线验收。“轨道信号场 Orbital Signal”的三端视觉与动效统一归下一阶段 G5，场地硬件联排仍属于正式版延期事项。

## 维护方式

当前项目由负责人本人长期单人维护。产品、前端、后端、视觉和测试仍按职责拆分，以便规划、审查和验收，但不假设固定有五名成员，也不把 AI 产出视为人类验收。

Demo v0 的当前边界：

- 同一局域网内运行 `/welcome`、`/admin` 和 `/screen`；
- 六阶段使用合成数据形成真实持久化与实时联动；
- 不进行公网部署，不接真实名单，不写实体 NFC，不接 AI 审核服务；
- 正式活动、硬件、印刷、域名和真实数据方案后续单独确认。

实体物料采购、付款、供应商下单、样品测试和到货验收均属于正式版延期事项，不阻塞 Demo v0。

## 协作规则

- GitHub Issue、分支和文档是开发任务与验收的正式记录；即时通信仅作可选通知渠道。
- 原则上一个 Issue 对应一个功能分支和一个 Pull Request；Demo v0 的跨模块基线以 `docs/DECISIONS.md` 中的已确认例外为准。
- 不直接向 `main` 推送；AI 也只能在独立分支工作。
- AI 生成的代码由对应人类负责人审查，不能自行验收。
- 真实姓名、学号、手机号、名单、密钥、数据库和现场导出文件不得进入仓库。

详细规则见 [CONTRIBUTING.md](CONTRIBUTING.md)。
